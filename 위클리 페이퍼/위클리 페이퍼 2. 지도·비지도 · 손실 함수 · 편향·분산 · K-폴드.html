실습 해설

지도 학습과 비지도 학습의 차이는 무엇인가요?

한 줄 요약 지도 학습은 정답(레이블)이 붙은 데이터로 입력에서 정답으로 가는 관계를 배우고, 비지도 학습은 정답 없이 데이터 자체의 구조(군집·차원·이상 패턴)를 찾는다. 둘을 가르는 기준은 과제 이름이 아니라 학습에 정답을 쓰느냐이다.

원래사진에 있는 물체를 분류하는 것이 지도 학습의 예입니다. 정정정답 레이블이 붙은 사진으로 분류 모델을 학습할 때 지도 학습입니다. 레이블 없이 비슷한 사진끼리 묶는다면 같은 사진 데이터라도 비지도 학습(군집화)입니다.

보충 둘 사이에 있는 학습 방식

보충 · 준지도 학습

정답이 일부만 있다

레이블 있는 소량 데이터와 레이블 없는 대량 데이터를 함께 씁니다. 레이블을 다는 비용이 클 때 씁니다 (예: 의료 영상).

보충 · 자기지도 학습

데이터가 스스로 정답을 만든다

사람이 레이블을 달지 않고, 데이터의 일부를 가린 뒤 맞히게 합니다. 대규모 언어 모델의 사전 학습(다음 단어 예측)이 대표적입니다.

보충 · 강화 학습

정답 대신 보상

정답을 직접 주지 않고, 행동의 결과로 받는 보상이 커지도록 학습합니다 (예: 게임, 로봇 제어).

보충 · 실무에서는 둘을 함께 쓴다

비지도 학습의 결과가 지도 학습의 재료가 되는 경우가 많습니다. 예를 들어 K-평균으로 만든 고객 군집 번호를 특성으로 추가해 이탈 예측 모델에 넣거나, PCA로 차원을 줄인 뒤 분류 모델을 학습합니다. 또한 비지도 학습이 만든 군집에는 이름이 없습니다. 실험 1의 오른쪽 군집 색은 왼쪽 등급 색과 일치하지 않을 수 있고, 각 군집이 어떤 고객인지는 사람이 특성을 보고 해석해야 합니다.

지도 학습은 입력과 정답 레이블을 함께 주고 입력에서 정답으로 가는 관계를 학습하는 방식이고, 분류와 회귀가 대표적입니다. 비지도 학습은 정답 없이 데이터만으로 군집화, 차원 축소, 이상 탐지처럼 숨은 구조를 찾습니다. 그래서 지도 학습은 정답과 비교해 정확도나 RMSE로 평가하지만, 비지도 학습은 실루엣 계수 같은 내부 지표와 도메인 해석이 필요합니다. 그 사이에 일부만 레이블을 쓰는 준지도 학습, 데이터에서 정답을 스스로 만드는 자기지도 학습도 있습니다.

손실 함수(loss function)란 무엇이며, 왜 중요한가요?

한 줄 요약 손실 함수는 예측이 정답에서 얼마나 틀렸는지를 하나의 숫자로 바꾼 것이고, 모델은 이 숫자를 줄이는 방향으로 파라미터를 고친다. 그래서 무엇을 얼마나 틀렸다고 볼지 정하는 손실 함수가 모델이 무엇을 배울지를 정한다.

2 · 핵심 정리와 보충
정정 · 손실 함수와 평가 지표는 다르다
원래손실함수를 통해 모델의 성능을 평가하고, 이를 통해 모델이 데이터를 얼마나 잘 예측하는지 파악할 수 있습니다. 정정손실 함수는 주로 학습 방향을 정하는 기준입니다. 최종 성능은 검증·테스트 데이터에서 목적에 맞는 평가 지표(정확도, F1, ROC-AUC, MAE 등)로 따로 판단합니다. 훈련 손실이 작아도 훈련 데이터에만 과적합했다면 새 데이터에서는 성능이 나쁠 수 있습니다.
손실 함수평가 지표

누가 쓰나최적화 알고리즘 (경사 하강법)사람, 의사 결정

예 (분류)교차 엔트로피정확도, 정밀도, 재현율, F1, ROC-AUC

정확도를 손실로 직접 쓰기 어려운 이유: 파라미터를 조금 바꿔도 정확도는 계단처럼 변하거나 그대로여서 기울기가 거의 모든 곳에서 0입니다. 그래서 학습은 교차 엔트로피로 하고, 평가는 정확도나 F1로 합니다.

보충 · 과적합은 훈련 손실로 안 보인다

개념도입니다. 훈련 손실은 계속 줄어도 검증 손실이 다시 오르기 시작하면 그때부터 과적합입니다. 검증 손실이 가장 낮은 지점에서 멈추는 것이 조기 종료(early stopping)입니다.

보충 · 용어 정리
  • 손실(loss): 샘플 하나의 오차
  • 비용(cost): 전체 데이터에 대한 손실의 평균
  • 목적 함수(objective): 실제로 최소화하는 식. 정규화 항이 들어가기도 한다: 비용 + λ‖w‖²

교재와 라이브러리마다 세 용어를 섞어 쓰는 경우가 많습니다.

손실 함수는 모델의 예측이 정답과 얼마나 다른지를 하나의 숫자로 나타낸 함수이고, 학습은 이 값을 줄이도록 경사 하강법으로 파라미터를 고치는 과정입니다. 어떤 손실을 고르느냐가 모델이 무엇을 중요하게 배울지를 정합니다. 예를 들어 MSE는 큰 오차를 제곱해서 이상치에 민감하고, MAE는 덜 민감하며, 분류에서는 교차 엔트로피를 주로 씁니다. 다만 손실은 학습용 기준이므로, 최종 성능은 검증 데이터에서 정확도나 F1처럼 목적에 맞는 평가 지표로 따로 판단합니다.

실습 해설

모델 학습 시 발생할 수 있는 편향과 분산에 대해 설명하고, 두 개념의 관계에 대해 설명해 주세요.

한 줄 요약 편향은 모델이 평균적으로 실제 규칙에서 비켜난 정도, 분산은 학습 데이터가 바뀔 때 예측이 흔들리는 정도다. 모델을 복잡하게 하면 편향은 줄고 분산은 커지는 경향이 있어 검증 오차가 가장 낮은 복잡도를 고르지만, 늘 한쪽을 내줘야 하는 법칙은 아니다.
1 · 그림·표

핵심 과녁으로 보는 편향과 분산

기대 테스트 오차 = 편향² + 분산 + 잡음 σ²

제곱 오차 기준의 분해입니다. 잡음은 데이터 자체의 무작위성이라 어떤 모델로도 줄일 수 없습니다. 그래서 기대 테스트 오차는 σ²보다 낮아질 수 없습니다.

정정 · 원래 해설에서 단정하거나 섞어 쓴 부분
원래편향과 분산은 Trade-off 관계에 있습니다. 즉, 하나를 줄이면 다른 하나가 증가하는 경향이 있습니다. 정정모델 복잡도를 조절할 때 그런 경향이 있다는 뜻이지, 항상 성립하는 법칙은 아닙니다. 실험 3에서 학습 데이터를 15개에서 100개로 늘리면 편향은 거의 그대로인데 분산이 줄어듭니다. 좋은 특성, 정규화, 앙상블도 한쪽을 크게 내주지 않고 오차를 줄일 수 있습니다.
원래저편향, 고분산: 훈련 데이터에 대해서는 매우 정확한 예측을 할 수 있습니다. 정정훈련 데이터에서 정확한 것은 과적합의 증상이지 저편향의 정의가 아닙니다. 편향은 여러 데이터셋으로 학습한 모델들의 평균 예측이 실제 규칙과 얼마나 다른지이고, 분산은 그 예측들이 얼마나 흩어지는지입니다.
보충 · 세 용어 구분
  • 편향: 평균 예측이 실제 규칙에서 벗어난 정도
  • 분산: 학습 데이터가 조금 바뀔 때 예측이 달라지는 정도
  • 과적합: 훈련 오차는 작지만 새 데이터의 오차는 큰 상태. 고분산이 주된 원인
보충 · 앙상블과 편향·분산
  • 배깅 (랜덤 포레스트): 여러 모델의 예측을 평균내 주로 분산을 줄인다
  • 부스팅 (XGBoost 등): 앞 모델의 오차를 이어서 고쳐 주로 편향을 줄인다

일반적인 설명이며, 하이퍼파라미터에 따라 부스팅도 과적합할 수 있습니다.

보충 · 고전적 U자 곡선의 예외

매우 큰 신경망에서는 파라미터 수가 데이터 수를 넘어선 뒤 테스트 오차가 다시 내려가는 이중 하강(double descent) 현상이 보고되었습니다. 편향-분산 균형은 출발점이 되는 직관이고, 모든 모델에 그대로 맞는 규칙은 아닙니다.

편향은 모델이 평균적으로 실제 규칙에서 얼마나 벗어나는지, 분산은 학습 데이터가 바뀔 때 예측이 얼마나 흔들리는지를 뜻합니다. 제곱 오차 기준으로 테스트 오차는 편향 제곱, 분산, 줄일 수 없는 잡음의 합으로 나뉩니다. 모델이 단순하면 패턴을 놓쳐 편향이 커지고, 복잡하면 잡음까지 외워 분산이 커지는 경향이 있어서, 검증 오차가 가장 낮은 복잡도를 고릅니다. 다만 항상 맞바꾸는 관계는 아니어서, 데이터를 늘리거나 정규화와 앙상블을 쓰면 분산을 줄일 수 있습니다.

고객 구매 금액 데이터가 오른쪽으로 심하게 치우친 분포를 보여요. 팀장님이 '평균 구매 금액이 5만원이니 다들 5만원 정도 쓴다고 보면 되겠네요'라고 말해요. 이 말에 어떻게 답할 건가요?

한 줄 요약 평균 5만 원은 1인당 매출로는 맞는 숫자지만 '보통 고객'을 대표하지 않을 수 있다. 중앙값이 얼마인지는 평균만으로 알 수 없으므로, 숫자를 짐작해 말하지 말고 실제 데이터로 중앙값·사분위수·평균 미만 고객 비율을 계산해서 답한다.
1 · 그림·표
실험 6 평균은 똑같이 5만 원, 치우침만 바꿔 보기 예시 · 로그정규분포를 가정한 가상의 구매 금액
평균을 5만 원으로 고정하고 치우침 정도만 바꿉니다. 중앙값, 평균 미만 고객 비율, 상위 10% 고객의 매출 비중이 얼마나 달라지는지 보세요. 값은 로그정규분포의 식으로 정확히 계산했습니다. 실제 데이터가 이 분포를 따른다는 뜻은 아닙니다.

2 · 핵심 정리와 보충
정정 · 1차 답안에 근거 없는 수치를 넣었다 (가장 큰 오류)
원래실제로 확인해 보면 중앙값은 2만 원 정도이고, 고객의 70% 이상이 평균보다 적게 쓸 가능성이 큽니다. 정정문제에는 중앙값도 비율도 주어지지 않았습니다. 실험 6처럼 같은 평균 5만 원이라도 치우침 정도에 따라 중앙값과 평균 미만 비율은 크게 달라집니다. 면접에서 짐작한 숫자를 말하면 '그 숫자는 어디서 나왔나요?'라는 질문에 답할 수 없습니다.
원래상위 10% 고객이 전체 매출의 60%를 차지합니다 같은 파레토 분석 정정계산한 결과가 아니라 예시라는 점을 분명히 해야 합니다. 이렇게 말합니다: '상위 10% 고객의 매출 비중을 계산해 보겠습니다.'
보충 · '평균 > 중앙값'도 경향이다

오른쪽으로 치우친 분포에서는 평균이 중앙값보다 큰 경우가 많지만, 수학적으로 항상 성립하는 규칙은 아닙니다. 그래서 이것도 짐작하지 말고 계산해서 확인합니다.

보충 · 평균의 정의부터 확인
  • 구매가 없는 고객(0원)이 포함된 평균인가, 구매 고객만의 평균인가
  • 극단값이 진짜 고객인가: B2B 대량 구매, 테스트 계정, 환불 미반영, 중복 결제
보충 · 말하는 방식

'틀렸습니다'가 아니라 '평균은 맞고, 목적에 따라 함께 볼 지표가 있습니다'로 시작합니다. 반박보다 대안 지표와 근거를 바로 제시하는 것이 핵심입니다.

평균 5만 원은 맞는 숫자이고, 총매출을 추정할 때는 평균이 맞는 지표입니다. 다만 분포가 오른쪽으로 치우쳐 있으면 소수의 고액 구매자가 평균을 끌어올려서, 평균보다 적게 쓰는 고객이 더 많을 수 있습니다. 그래서 다들 5만 원 정도 쓴다고 보기는 어렵습니다. 중앙값과 사분위수, 평균 미만 고객 비율, 상위 고객의 매출 비중을 실제 데이터로 계산해서 히스토그램과 함께 보여드리겠습니다. 전형적인 고객을 보시려는 거라면 중앙값과 고객 세그먼트로 보시는 게 정확합니다.

면접 3
면접 · 전문가 답변

서로 다른 두 팀이 각자 관리하던 고객 데이터를 하나로 합쳐야 해요. 두 데이터 모두 고객 ID가 중복되거나 값이 다르게 기록된 행이 있고, 결측치도 섞여 있어요. 어떤 순서로 이 작업에 접근할 건가요?

한 줄 요약 먼저 한 행이 무엇을 뜻하는지와 어느 쪽을 기준으로 삼을지를 합의하고, 표준화 → 각 데이터 안의 중복 정리 → 키 매칭과 병합 → 값 충돌 해결 → 결측 보완 → 검증 순서로 간다. 결측은 병합 뒤에 채워야 다른 팀 데이터의 실제 값을 쓸 수 있다.
1 · 그림·표
데이터 단위·기준 확인한 행 = 고객 한 명인가, 주문·상담 기록인가. 값이 다르면 어느 팀을 기준으로 할지 합의
프로파일링행 수, 고유 ID 수, 컬럼별 결측률. 나중에 검증할 기준 숫자
표준화컬럼명·타입, 전화번호·이메일 형식, 코드값 통일
내부 중복 정리고객 마스터일 때만, 합의한 규칙으로 (예: 최신 updated_at)
키 매칭·병합ID로 병합. ID 체계가 다르면 이메일·전화번호로 매칭
충돌 해결컬럼별 규칙 적용, 충돌한 건은 로그로 남김
결측 보완상대 데이터 값으로 먼저 채우고, 남은 것만 대체하거나 표시
검증·문서화행 수, ID 유일성, 합계 대조. 규칙을 문서로 공유

충돌을 규칙으로 해결한 값상대 데이터로 채운 결측
예시 코드
def standardize(df):
    df = df.copy()
    df["phone"] = df["phone"].str.replace(r"\D", "", regex=True)   # 숫자만 남김
    df["email"] = df["email"].str.strip().str.lower()
    df["updated_at"] = pd.to_datetime(df["updated_at"])
    return df

a, b = standardize(a), standardize(b)

# 0. 한 행 = 고객 한 명인지 확인. 주문·상담 기록이면 아래 중복 제거를 하면 안 된다
print(a["customer_id"].is_unique, b["customer_id"].is_unique)

# 3. 고객 마스터일 때만: 고객별 최신 행 유지
a = a.sort_values("updated_at").drop_duplicates("customer_id", keep="last")
b = b.sort_values("updated_at").drop_duplicates("customer_id", keep="last")

# 4. 감사용 outer 병합: 한쪽에만 있는 고객 표시, 키 유일성 검증
m = a.merge(b, on="customer_id", how="outer", suffixes=("_a", "_b"),
            indicator=True, validate="one_to_one")

# 5. 충돌 기록
conflict = m["phone_a"].notna() & m["phone_b"].notna() & (m["phone_a"] != m["phone_b"])
m.loc[conflict, ["customer_id", "phone_a", "phone_b"]].to_csv("conflicts.csv", index=False)

# 5~6. 최신 쪽 우선, 그쪽이 비었으면 다른 쪽 값으로 보완
b_newer = m["updated_at_b"] > m["updated_at_a"]           # 한쪽이 NaT면 False → A 우선
m["phone"] = np.where(b_newer,
                      m["phone_b"].combine_first(m["phone_a"]),
                      m["phone_a"].combine_first(m["phone_b"]))

# 7. 검증
assert m["customer_id"].is_unique
print(m["_merge"].value_counts())
2 · 핵심 정리와 보충
정정 · 1차 답안에서 빠졌거나 무조건으로 쓴 부분
원래각 데이터 안에서 먼저 중복 제거: a.sort_values("updated_at").drop_duplicates("customer_id", keep="last") 정정이 코드는 한 행이 고객 한 명인 마스터 데이터일 때만 맞습니다. 한 행이 주문이나 상담 기록이라면 같은 고객 ID가 여러 번 나오는 것이 정상이고, 이 코드를 쓰면 고객별 마지막 기록 한 건만 남고 나머지가 지워집니다. 그래서 데이터 단위 확인이 첫 단계입니다.
원래완전히 같은 행은 삭제합니다. 정정거래 ID나 정확한 발생 시각이 없으면 같은 고객이 같은 날 같은 금액으로 두 번 산 기록일 수도 있습니다. 수집 방식과 업무 규칙을 확인한 뒤 지웁니다.
원래한쪽 데이터의 빈 값을 다른 쪽 값으로 먼저 채웁니다(combine_first). 정정A.combine_first(B)는 A에 값이 있으면 A를 씁니다. 어느 쪽이 우선인지를 규칙으로 먼저 정해야 합니다(위 코드에서는 더 최신인 쪽).
원래ID 체계가 같으면 outer join으로 합칩니다. 정정outer join은 누락된 고객을 확인하는 감사 단계에 좋습니다. 최종 결과는 목적에 따라 inner나 left join이 맞을 수 있습니다.
보충 · 왜 이 순서인가
  • 표준화가 중복 처리보다 먼저: 형식만 다른 값이 가짜 중복과 가짜 충돌로 보이기 때문 (예시의 C001 이메일)
  • 결측 보완이 병합보다 뒤: 병합 전에 채우면 다른 팀에 있는 실제 값을 추정값으로 덮게 된다 (예시의 C003)
보충 · ID 체계가 다를 때

정규화한 이메일·전화번호로 같은 사람을 찾는 개체 매칭(entity resolution)이 필요합니다. 이름 유사도 같은 퍼지 매칭은 잘못 합칠 위험이 있으므로 사람이 검토할 후보로만 씁니다.

보충 · 개인정보

전화번호·이메일로 두 부서의 데이터를 합치는 것은 개인정보 처리에 해당할 수 있습니다. 이용 목적과 접근 권한을 확인하고, 필요하면 해시한 값으로 매칭합니다.

먼저 두 데이터에서 한 행이 고객 한 명인지, 주문 같은 기록인지 확인하고, 값이 다를 때 어느 쪽을 기준으로 할지 두 팀과 합의하겠습니다. 그다음 결측률과 고유 ID 수를 파악하고 전화번호, 이메일 형식을 표준화합니다. 표준화를 먼저 해야 가짜 중복과 가짜 충돌이 사라집니다. 이후 각 데이터의 중복을 규칙대로 정리하고, ID로 병합하면서 한쪽에만 있는 고객과 값 충돌을 기록합니다. 결측은 병합 후 상대 데이터 값으로 먼저 채우고, 마지막으로 행 수와 ID 유일성을 검증해 규칙을 문서로 남기겠습니다.
