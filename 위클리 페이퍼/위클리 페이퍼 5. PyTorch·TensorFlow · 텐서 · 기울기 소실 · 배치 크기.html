Q1
실습 해설

딥러닝 프레임워크인 PyTorch와 TensorFlow를 비교해보세요.

한 줄 요약

PyTorch와 TensorFlow는 모두 텐서 연산 · 자동 미분 · GPU 가속 · 분산 학습 · 배포를 갖춘 딥러닝 프레임워크다. TensorFlow 2.0(2019) 이후 둘 다 즉시 실행(eager)이 기본이고, 필요할 때 그래프로 컴파일한다. 그래서 "PyTorch는 연구용, TensorFlow는 배포용"이라는 구분은 이제 맞지 않는다.

지금의 차이는 생태계와 배포 경로다.

  • PyTorch: 논문 구현 · 대형 언어 모델 · Hugging Face의 사실상 표준
  • TensorFlow: Keras · TFX · TF Serving · LiteRT로 이어지는 운영 도구와 TPU 지원

따라서 고르는 기준은 인기가 아니라 팀의 기존 스택, 배포 대상, 쓰려는 사전 학습 모델이다.

TensorFlow · Keras · fit()이 루프를 돌리고 장치는 자동
import tensorflow as tf
import keras

model = keras.Sequential([keras.Input((20,)),
    keras.layers.Dense(64, activation="relu"),
    keras.layers.Dense(1)])
loss_fn = keras.losses.BinaryCrossentropy(from_logits=True)
opt = keras.optimizers.AdamW(learning_rate=1e-3)

model.compile(optimizer=opt, loss=loss_fn)
model.fit(dataset, epochs=10)         # 루프를 Keras가 제공

@tf.function                          # 직접 루프: 그래프로 추적
def train_step(x, y):
    with tf.GradientTape() as tape:
        loss = loss_fn(y, model(x, training=True))
    grads = tape.gradient(loss, model.trainable_variables)
    opt.apply_gradients(zip(grads, model.trainable_variables))
    return loss

        원래 · 실습 해설최근에는 배포 도구인 TorchServe로 프로덕션 환경에서도 많이 사용되고 있습니다.
        

          
정정TorchServe는 2025년부터 제한적 유지보수(Limited Maintenance) 상태입니다. 공식 문서에 새 기능 · 버그 수정 · 보안 패치 계획이 없다고 공지되어 있어, 신규 프로젝트의 대표 배포 도구로 볼 수 없습니다.

          
지금 PyTorch 모델은 용도에 따라 다음 경로로 배포합니다.

          
    
            
  • 일반 서버: torch.export + AOTInductor, ONNX → ONNX Runtime · TensorRT, Triton Inference Server
    • 
            
  • 대형 언어 모델: vLLM · SGLang 같은 전용 서빙 엔진
    • 
            
  • 모바일 · 엣지: ExecuTorch
    • 
          

          
작성 답안은 이 점을 이미 바르게 지적했습니다.

        

      

      

        원래 · 실습 해설PyTorch는 유연성과 사용성이 강점이고, TensorFlow는 배포와 확장성에서 더 유리하다고 볼 수 있습니다.
        

          
정정확장성은 PyTorch의 약점이 아닙니다. DDP · FSDP · 텐서 병렬로 수천 개 GPU에서 학습하며, Meta의 Llama 같은 대형 언어 모델 다수가 PyTorch로 학습됩니다.

          
TensorFlow가 앞서는 부분은 확장성 일반이 아니라 운영 도구(TFX · TF Serving · LiteRT)와 TPU 통합입니다. 둘 다 학습부터 배포까지 할 수 있고, 실제 차이는 생태계와 기존 스택입니다.

  • 중간값을 print로 바로 확인하기
    •

    • 
        

        
PyTorch는 코드를 실행하는 순간 계산이 일어나(define-by-run) Python 디버거를 그대로 쓸 수 있었고, 이것이 연구자들이 옮겨 간 핵심 이유입니다.

      

      
보충 · 세 번째 선택지
JAX와 Keras 3

        
JAX는 NumPy와 같은 문법에 grad · jit · vmap 같은 함수 변환을 더한 프레임워크로, 구글 내부 연구(Gemini 등)의 주력입니다.

        
Keras 3는 같은 코드를 JAX · TensorFlow · PyTorch 백엔드에서 실행합니다. 그래서 "Keras = TensorFlow"도 이제는 정확하지 않습니다.

      

      
보충 · 실무에서 먼저 확인할 것

    • 
          
  • 사전 학습 모델: 쓰려는 모델과 예제 코드가 어느 프레임워크에 있는지가 선택을 사실상 결정하는 경우가 많습니다.
    • 
        

      

    


    

      
PyTorch와 TensorFlow는 둘 다 텐서 연산, 자동 미분, GPU 가속, 분산 학습, 배포를 갖춘 딥러닝 프레임워크입니다.

      
원래 TensorFlow 1은 그래프를 먼저 정의하고 Session으로 실행해서 디버깅이 어려웠고, PyTorch는 코드를 실행하는 순간 그래프를 기록하는 즉시 실행 방식이라 연구자들이 선호했습니다. 지금은 TensorFlow 2가 즉시 실행을 기본으로 하고 PyTorch도 torch.compile로 컴파일하기 때문에, 실행 방식의 차이는 거의 사라졌습니다.

      
남은 차이는 생태계입니다. PyTorch는 논문 구현, Hugging Face, 대형 언어 모델 학습의 표준이고, TensorFlow는 Keras, TF Serving, LiteRT로 이어지는 운영 도구와 TPU 지원이 강점입니다. 참고로 TorchServe는 유지보수가 중단돼서, PyTorch 배포는 torch.export, ONNX, vLLM 같은 경로를 씁니다.

      
그래서 저는 팀의 기존 스택, 배포 대상, 쓰려는 사전 학습 모델을 기준으로 고르겠습니다.

      보충 · 실습 해설을 더 정확하게
      
그래프를 기록하는 주체. "requires_grad=True로 설정된 텐서는 계산 그래프를 기록한다"는 정확히 말하면, 그 텐서가 참여한 연산을 autograd 엔진이 기록한다는 뜻입니다.

      
    
        
  • 결과 텐서마다 자신을 만든 연산(grad_fn)이 붙는다.
    • 
        
  • backward()는 이 고리를 거꾸로 따라가 잎 텐서의 .grad에 기울기를 더한다(누적).
    • 
        
  • 그래프는 역전파가 끝나면 해제되어 매 반복 새로 만들어진다(실험 1). 같은 그래프로 두 번 역전파하려면 retain_graph=True가 필요하다.
    • 
      

      
장치 이동. 텐서의 .to(device)는 새 텐서를 돌려주므로 x = x.to(device)처럼 대입해야 합니다. 제자리에서 옮겨지는 것은 모델(nn.Module)의 .to()뿐입니다.

    


    

      
보충 · dtype 기본값의 함정
float64 텐서를 float32 모델에 넣으면 오류

        
NumPy로 전처리한 배열을 torch.from_numpy()로 바꾸면 float64 텐서가 됩니다. 이것을 float32인 nn.Linear에 넣으면 다음 오류가 납니다.

        
RuntimeError: mat1 and mat2 must have the same dtype

        
해결: .float()를 붙이거나 처음부터 np.float32로 만듭니다. GPU는 float32 · bfloat16 연산이 float64보다 훨씬 빠르기 때문에 딥러닝의 기본값이 float32입니다.

y = x.sigmoid() 뒤에 y.mul_(2)를 하면, 시그모이드의 역전파에 필요한 y가 바뀌어 오류가 납니다.

PyTorch는 텐서마다 버전 번호를 두어 이런 덮어쓰기를 잡아냅니다. NumPy에는 없는 제약입니다.

PyTorch 텐서는 dtype, shape, device를 가진 다차원 배열이고, 인덱싱이나 브로드캐스팅 규칙은 NumPy 배열과 거의 같습니다.

      
차이는 세 가지입니다. 첫째, to(device)로 GPU 메모리에 올려 병렬 연산을 할 수 있습니다. 둘째, requires_grad가 켜진 텐서가 참여한 연산은 autograd가 기록해서, backward 한 번으로 모든 파라미터의 기울기를 계산합니다. 셋째, 기본 실수 타입이 NumPy는 float64, PyTorch는 float32라서 from_numpy로 가져온 배열은 float으로 바꿔 줘야 합니다.

      
또 CPU에서는 from_numpy와 numpy 메서드가 메모리를 공유해서 한쪽을 바꾸면 다른 쪽도 바뀝니다. GPU 텐서나 기울기를 추적 중인 텐서는 detach, cpu, numpy 순서로 변환합니다.

방법기울기 흐름에 미치는 효과주의

He 초기화 (ReLU) · Xavier (tanh)층을 지나도 활성화와 기울기의 분산이 유지되도록 Var(W) = 2/fan_in 또는 2/(fan_in + fan_out)로 맞춘다초기화만으로는 학습 중 분포가 다시 틀어질 수 있다

          
잔차 연결hl = hl−1 + F(hl−1)이면 ∂hl/∂hl−1 = I + ∂F/∂h, 항등 경로로 기울기가 곱셈 없이 전달된다층이 깊으면 잔차 가지의 출력을 작게 시작해야 순전파 값이 폭주하지 않는다

          
배치·레이어 정규화각 층 입력을 평균 0·분산 1 근처로 맞춰 포화 구간에 들어가지 않게 한다배치 정규화는 작은 배치에서 불안정, 그때는 레이어·그룹 정규화

          
BCEWithLogitsLoss시그모이드와 교차 엔트로피를 합치면 출력층 기울기가 p − y로 단순해져 출력에서의 포화가 없다시그모이드 출력 + MSE는 출력층부터 기울기가 작아진다

          
기울기 클리핑너무 큰 기울기만 잘라 낸다폭발 대책이다. 작은 기울기를 키우지는 못한다

        
      

    


    

      
층별 기울기, 실제 갱신 비율, 시그모이드 포화를 한 스텝에서 함께 기록하기


import torch
from torch import nn

saturation = {}
def hook(name):
    def f(module, inputs, out):                       # 시그모이드 출력이 0·1에 붙은 비율
        saturation[name] = ((out < 0.01) | (out > 0.99)).float().mean().item()
    return f
for name, m in model.named_modules():
    if isinstance(m, nn.Sigmoid):
        m.register_forward_hook(hook(name))

loss = criterion(model(x), y)
optimizer.zero_grad(set_to_none=True)
loss.backward()
before = {n: p.detach().clone() for n, p in model.named_parameters()}
grad_norm = {n: (p.grad.norm().item() if p.grad is not None else None)
             for n, p in model.named_parameters()}         # None = 그래프 단절 의심
optimizer.step()
for n, p in model.named_parameters():                   # 실제로 얼마나 바뀌었나 (권장 경험치 ≈ 1e-3)
    update = (p.detach() - before[n]).norm() / (before[n].norm() + 1e-12)
    print(f"{n:24s} grad={grad_norm[n]} update/weight={update.item():.2e}")

    


    
2 · 핵심 정리와 보충


    

      정정 · 작성 답안에서 바로잡을 부분
      

        원래 · 작성 답안update_ratio = gradient_norm / (parameter_norm + 1e-12) … 입력층에 가까워질수록 gradient와 ratio가 지수적으로 작아진다면 기울기 소실의 강한 증거입니다.
        

          
정정이 값은 기울기 / 가중치 비율이지 갱신 비율이 아닙니다. 실제 갱신량은 학습률과 옵티마이저가 정합니다.

          
    
            
  • SGD: ‖ΔW‖ = 학습률 × ‖grad‖라서 두 비율이 비례한다.
    • 
            
  • Adam: 기울기를 그 크기의 이동 평균으로 나누므로, 기울기가 작아도 갱신은 덜 작아진다.
    • 
          

          
그래서 "입력층 가중치가 거의 그대로"라는 증상은 위 코드처럼 step() 전후 가중치 차이로 ‖ΔW‖/‖W‖를 직접 재서 확인해야 합니다.

          
다만 Adam의 보상에도 한계가 있습니다. 기울기가 분모에 더하는 ε(기본 10⁻⁸)보다 작아지거나, 부호가 잡음처럼 흔들려 이동 평균이 상쇄되면 갱신도 다시 작아집니다. 실험 3에서 SGD와 Adam의 변화율 비를 비교해 보세요.

        

      

    


    

      
보충 · 출력층 근처만 학습되는 이유
마지막 층은 곱셈을 거의 거치지 않는다

        
출력층의 기울기는 손실에서 한 번만 곱해져 내려오므로 크기가 정상입니다. 그래서 loss가 조금씩 줄어 겉으로는 "학습은 된다"고 보입니다.

        
실제로는 무작위로 초기화된 앞쪽 19개 층의 출력 위에서 마지막 몇 층만 맞추고 있는 상태라, 깊이의 이점을 전혀 쓰지 못합니다.

      

      
보충 · 시그모이드의 두 번째 문제
출력이 항상 양수다

        
시그모이드 출력은 0~1이라 평균이 0.5입니다. 다음 층 가중치의 기울기는 (뒤에서 온 기울기) × (이 입력)이므로, 입력이 모두 양수면 한 뉴런으로 들어가는 가중치들의 기울기 부호가 모두 같아집니다. 그 결과 갱신이 지그재그로 움직여 느려집니다.

        
tanh가 시그모이드보다 나은 이유가 바로 0 중심이라는 점입니다. Glorot & Bengio(2010)도 시그모이드 깊은 망에서 위쪽 층이 포화되는 현상을 보고했습니다.

      

      
보충 · 시그모이드가 맞는 자리
출력층과 게이트

        
"0~1 사이의 비율"이 필요한 곳에서는 시그모이드가 정답입니다.

        
    
          
  • 이진 분류의 출력층
    • 
          
  • LSTM · GRU의 게이트
    • 
          
  • 어텐션 마스크
    • 
        

        
문제는 깊이 방향으로 반복해서 곱해지는 은닉층에 쓰는 것입니다. 참고로 LSTM은 셀 상태를 더하기로 전달해 시간 방향의 기울기 소실을 줄인 구조입니다.

      

    


    

      
입력층 쪽 가중치만 거의 안 바뀐다면 시그모이드 때문에 생기는 기울기 소실을 가장 먼저 의심하겠습니다. 역전파는 층마다 시그모이드 미분값과 가중치를 곱하는데, 시그모이드 미분은 최대 0.25이고 출력이 0이나 1에 가까우면 거의 0이라서, 20층을 지나면 입력층 기울기가 지수적으로 작아집니다.

      
확인은 loss.backward 직후 층별 기울기 노름을 찍어서, 출력층에서 입력층으로 갈수록 로그 축에서 직선처럼 줄어드는지 봅니다. optimizer.step 전후 가중치 차이로 실제 갱신 비율도 재고, 활성화가 0과 1에 몰려 있는지도 보겠습니다. grad가 None인 경우는 그래프가 끊긴 다른 문제라 따로 구분하겠습니다.

      
해결은 은닉층을 ReLU나 GELU로 바꾸고 He 초기화를 쓰고, 잔차 연결과 배치나 레이어 정규화를 넣는 것입니다. 시그모이드는 출력층에만 두고 BCEWithLogitsLoss로 묶겠습니다. 기울기 클리핑은 폭발 대책이라 이 문제의 해결책은 아닙니다.

너무 작은 배치

import time, torch

def probe(batch_size, steps=20):
    torch.cuda.empty_cache(); torch.cuda.reset_peak_memory_stats()
    x = torch.randn(batch_size, *worst_case_shape, device="cuda")   # 가변 길이면 최대 길이로
    y = torch.randint(0, n_classes, (batch_size,), device="cuda")
    try:
        for i in range(steps + 3):
            if i == 3:                                   # 워밍업 뒤부터 측정
                torch.cuda.synchronize(); t0 = time.perf_counter()
            loss = criterion(model(x), y)
            loss.backward(); optimizer.step(); optimizer.zero_grad(set_to_none=True)
        torch.cuda.synchronize()                         # GPU는 비동기라 반드시 대기
        return batch_size * steps / (time.perf_counter() - t0), torch.cuda.max_memory_allocated() / 2**30
    except torch.cuda.OutOfMemoryError:
        return None
    # 측정용 스텝이 가중치를 바꾸므로, 실제 학습 전에 모델·옵티마이저를 새로 만든다

for bs in [16, 32, 64, 128, 256, 512]:
    print(bs, probe(bs))                                 # (초당 샘플 수, 최대 GB) 또는 None

import contextlib, torch

accum = 4                                                # 유효 배치 = 마이크로 배치 × 4 × GPU 수
scaler = torch.amp.GradScaler("cuda")
optimizer.zero_grad(set_to_none=True)
for step, (x, y) in enumerate(loader, start=1):
    x = x.to(device, non_blocking=True)                  # pin_memory=True와 짝: 전송을 계산과 겹침
    y = y.to(device, non_blocking=True)
    sync = step % accum == 0 or step == len(loader)      # 에포크 끝의 남은 배치도 반영
    ctx = contextlib.nullcontext() if (sync or not is_ddp) else model.no_sync()
    with ctx:
        with torch.autocast("cuda", dtype=torch.float16):
            loss = criterion(model(x), y) / accum        # 평균 loss라면 누적 횟수로 나눈다
        scaler.scale(loss).backward()
    if sync:
        scaler.unscale_(optimizer)
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(optimizer); scaler.update()
        optimizer.zero_grad(set_to_none=True)

    


    
2 · 핵심 정리와 보충


    

      정정 · 작성 답안에서 바로잡을 부분
      

        원래 · 작성 답안GPU 메모리가 부족할 때의 해결책 … 추가 방법: pin_memory=True, non_blocking=True로 데이터 전송 최적화, 데이터 로딩과 GPU 연산을 겹치도록 prefetch 적용
        

          
정정이 세 가지는 GPU 메모리를 줄이지 않습니다. 고정(페이지 잠금) CPU 메모리에서 GPU로 비동기 전송해 대기 시간을 줄이는 속도 최적화입니다. prefetch는 다음 배치를 미리 준비하므로 메모리를 오히려 조금 더 씁니다.

          
실제로 메모리를 줄이는 방법은 다음과 같습니다.

          
    
            
  • 마이크로 배치 축소 + 기울기 누적
    • 
            
  • AMP, 활성화 체크포인팅, 입력 크기 축소
    • 
            
  • 고정 부분을 GPU 여러 대에 나누는 FSDP · ZeRO, 8비트 옵티마이저
    • 
          

        

      

      

        원래 · 작성 답안큰 배치는 입력·활성화·기울기를 저장하기 위해 더 많은 GPU 메모리가 필요하고
        

          
정정배치에 비례하는 것은 입력과 활성화(그리고 역전파 중의 활성화 기울기)입니다. 파라미터 기울기는 파라미터와 크기가 같아서 배치가 1이든 1,000이든 같습니다(실험 4).

        

      

      

        원래 · 작성 답안DataLoader가 작은 미니배치만 순서대로 GPU에 전달하도록 구성합니다.
        

          
정정DataLoader는 CPU에서 배치를 만들어 돌려줄 뿐이고, GPU로 옮기는 것은 학습 루프의 .to(device)입니다.

          
100만 개가 CPU 메모리에도 다 들어가지 않으면, Dataset.__getitem__이 필요한 샘플만 디스크에서 읽도록(메모리 매핑, 샤드 파일 스트리밍) 만들어야 합니다.

        

      

    


    

      
보충 · 학습률은 배치와 짝이다
스케일링 규칙과 임계 배치 크기

        
    
          
  • SGD: 배치를 k배로 키우면 학습률도 k배로 하고 warm-up을 둔다 (선형 규칙, Goyal 외 2017)
    • 
          
  • Adam 계열: √k배가 이론적으로 더 맞다는 분석이 있다 (Malladi 외 2022)
    • 
        

        
어느 규칙이든 기울기 잡음이 충분히 작아지는 임계 배치 크기를 넘으면, 배치를 키워도 필요한 스텝 수가 줄지 않습니다(McCandlish 외 2018). 실험 5에서 선형 규칙이 무너지는 지점을 확인해 보세요.

      

      
보충 · 큰 배치의 일반화 논쟁
배치 탓인가, 스텝 수 탓인가

        
    
          
  • Keskar 외(2017): 큰 배치는 날카로운 최솟값으로 가서 일반화가 나쁘다.
    • 
          
  • Hoffer 외(2017), Shallue 외(2018): 학습률을 다시 맞추고 스텝 수를 충분히 주면 격차 대부분이 사라진다.
    • 
        

        
그래서 "큰 배치는 일반화가 나쁘다"보다 "같은 에포크 · 같은 학습률로 비교하면 나빠 보인다"가 정확합니다.

    • 
          
  • 가변 길이 데이터는 가장 긴 입력으로 시험해야 학습 도중 OOM이 나지 않습니다. 길이가 비슷한 샘플끼리 묶는 버킷팅도 낭비를 줄입니다.
    • 
        

      

    


    

      
100만 개를 GPU에 다 올릴 필요는 없습니다. 데이터는 디스크나 CPU 메모리에 두고, DataLoader가 CPU에서 만든 미니배치만 학습 루프에서 GPU로 옮깁니다.

      
배치 크기는 GPU 메모리로 먼저 정합니다. 학습 메모리는 파라미터, 기울기, 옵티마이저 상태처럼 배치와 무관한 부분과 배치에 비례하는 활성화로 나뉩니다. 그래서 배치를 16, 32, 64로 두 배씩 늘리면서 가장 긴 입력으로 최대 메모리와 초당 샘플 수를 재고, 처리량이 더 늘지 않거나 OOM 직전인 값보다 여유 있게 고릅니다. 원하는 유효 배치가 안 들어가면 기울기 누적, AMP, 활성화 체크포인팅을 씁니다.

      
배치가 너무 작으면 GPU를 다 못 쓰고 기울기 잡음이 커서 학습이 느리고, 배치 정규화도 불안정합니다. 너무 크면 메모리가 부족하고 에포크당 업데이트 수가 줄어 학습률을 키워야 하는데, 어느 지점부터는 키워도 빨라지지 않습니다. 그래서 배치를 바꾸면 학습률과 warm-up을 검증 데이터로 다시 맞추겠습니다.

Q1 작성 답안정확실행 방식·자동 미분·컴파일·분산·배포 기준의 비교표, TorchServe·LiteRT·ExecuTorch 현황, 이분법 비판TF 1.x의 그래프 우선 방식이 차이의 출발점이라는 배경, JAX·Keras 3, Hugging Face 생태계 추가

        
Q2 텐서 vs 배열 (실습 해설)보완GPU 가속과 autograd가 핵심 차이기본 dtype 차이(float32 vs float64), 메모리 공유, 텐서의 .to()는 대입 필요, 그래프는 연산이 기록된다는 표현

        
Q2 작성 답안정확메모리 공유 실험 코드와 기울기 2xᵢ/3 계산, detach().cpu().numpy()dtype 기본값 함정, 제자리 연산과 autograd 버전 검사, GPU 비동기 실행 추가

        
면접 1 20층 시그모이드 (작성 답안)보완기울기 소실 진단, 0.25²⁰ 계산, grad None과 작은 grad 구분, ReLU·초기화·잔차·정규화, 클리핑은 폭발 대책기울기/가중치 비율을 갱신 비율이라 부른 점. 실제 갱신은 step 전후 차이로 재야 하고 Adam은 작은 기울기를 일부 보상함

        
면접 2 배치 크기 (작성 답안)보완미니배치 공급, 두 배씩 늘리며 측정, 업데이트 수 계산, 기울기 누적과 유효 배치, BN 차이pin_memory·non_blocking·prefetch는 메모리 절약이 아님. 파라미터 기울기는 배치와 무관. DataLoader는 GPU로 옮기지 않음. 학습률 스케일링 규칙과 임계 배치 추가
